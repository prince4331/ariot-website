### Context

Phase 2 requires admin/CMS access now, and Phase 3 (customer ecommerce) and Phase 5 (B2B/team accounts) require customer and organizational identities later. The project is a small R&D-stage startup (ARIOT Technologies) on a budget. The stack is frozen: Next.js 16 App Router + React 19, Prisma 7 + PostgreSQL 16, TypeScript strict, server-side RBAC planned (`server/auth/permissions.ts`). The schema already mirrors the Auth.js Prisma model shape — `User` (with `passwordHash`, `email`, soft delete), `Session` (`tokenHash`, `expiresAt`), `Role`, and `UserRole` join — and `DATABASE_SCHEMA_PLAN.md` §1 is explicitly designed so each later phase only *adds* identity fields (`Customer`, `Account`, `AccountMember`, `B2B` in Phase 5) without refactoring core types.

### Options considered

1. **Auth.js / NextAuth v5 + Prisma Adapter** — open-source, MIT-licensed, App Router native (`auth()` helper, route handlers), first-class Prisma adapter that maps onto the existing `User`/`Session`/`Role`/`UserRole` models, supports credentials + OAuth (GitHub/Google) + email providers, JWT or DB sessions, no per-seat fee.
2. **Clerk** — hosted auth SaaS, polished prebuilt UI, but per-MAU cost, hosted user store, vendor lock-in, and limited control over the DB-resident RBAC model the project already defines.
3. **Custom authentication** — full in-house passwords/sessions. Maximum control but re-implements battle-tested primitives (argon2id hashing, CSRF, session rotation, OAuth) and raises the security burden unacceptable for a small team.
4. **Lucia (open-source)** — was a strong open-source alternative, but the project is archived/unmaintained as of 2025; adopting an unmaintained auth library now is a long-term maintenance risk, so it was not selected.

### Why Auth.js + Prisma Adapter was chosen

- **Free / open-source first** — MIT licensed, no per-seat or MAU fees; fits a bootstrap budget.
- **Security** — maintained by a large OSS community, supports OAuth (no passwords for admins where possible), integrates with the project's argon2id `passwordHash` field and `Session.tokenHash` strategy, and works with existing HTTP-only/Secure/SameSite cookie + CSRF (Server Action) baseline.
- **Next.js App Router fit** — v5 is built for App Router (`auth()`, middleware optional, route handlers). No CSR-only auth.
- **Prisma/PostgreSQL fit** — the Prisma adapter maps directly onto the already-defined `User`/`Session`/`Role`/`UserRole` models; no schema rework.
- **RBAC suitability** — Auth.js owns *authentication* (who you are); `requireRole`/`requirePermission` helpers in `server/auth/permissions.ts` own *authorization*, layered on the existing `Role.permissions` JSON + `UserRole` join. Clean separation, no client-side-only checks.
- **Admin, customer, and B2B suitability** — same identity core serves `super_admin`/`content_admin`/etc. now, `Customer` in Phase 3, and `Account`/`AccountMember` B2B teams in Phase 5, all without leaving the Prisma data model.
- **Low vendor lock-in / maintainable** — self-hosted on our own Postgres; sessions and users are our data; we can migrate the adapter or swap providers later without losing the user table.
- **Startup practicality / deployment** — runs as ordinary Next.js route handlers on Vercel or any Node host; no external auth service to provision or pay for.

### Why alternatives were rejected

- **Clerk** — rejected: recurring per-MAU cost, hosted user directory (vendor lock-in), and it would duplicate/compete with the already-defined DB RBAC model. Only justifiable if ARIOT later wants to offload all auth engineering; not warranted at this stage.
- **Custom auth** — rejected: unacceptable security burden for a small team (must hand-roll hashing, session storage, CSRF, OAuth, brute-force protection) and slower to ship. Approved only as a fallback if a future requirement cannot be met by Auth.js.
- **Lucia** — rejected: archived/unmaintained upstream; adopting it now creates a future maintenance/security liability.

### Security implications

- Admin sign-in should prefer **OAuth (GitHub/Google)** where possible; credentials (email + argon2id `passwordHash`) only where required.
- Passwords never stored in plaintext; `passwordHash` already nullable for OAuth-only users.
- Sessions: DB-backed (`Session` table with `tokenHash`, `expiresAt`) or JWT — decision deferred to Step 2.2.2, but tokens stay HTTP-only, Secure, SameSite=Lax, with quarterly secret rotation (per `TECH_ARCHITECTURE.md` §11).
- RBAC enforced **server-side only** (`(admin)` layout + every server action) via `requireRole`/`requirePermission`; no admin data behind client-only checks.
- Public auth mutation endpoints (`/api/auth/*`, password-reset) must be rate-limited (extends existing `server/rate-limit.ts`).
- No real credentials, hashes, session tokens, OAuth secrets, or admin emails committed to repo, `.env.example`, seeds, or docs.

### Cost implications

- **$0** for the auth library itself. Only infra we already pay for (Postgres, Next.js host). No Clerk MAU fees. Optional paid OAuth providers are not required.

### Vendor lock-in implications

- Minimal. User/session/role data lives in our Postgres via the Prisma adapter. If Auth.js is ever replaced (e.g., by a custom layer or different provider), the `User`/`Session`/`Role`/`UserRole` tables remain the source of truth and migrate cleanly.

### Future migration considerations

- The adapter boundary is the only Auth.js-specific coupling. Swapping providers means re-implementing the `auth()`/`getSession()` surface and the `server/auth/permissions.ts` session read — the DB models stay.
- Phase 3 (`Customer`) and Phase 5 (`Account`, `AccountMember`, B2B seats) extend the **same** `User` identity; no new auth provider needed.

## D-035 — Auth Provider Selection: Better Auth (replaces Auth.js, Step 2.2.2)

- **Decision date**: 2026-07-10
- **Selected provider**: **Better Auth** (MIT, self-hosted) + official Prisma adapter (`better-auth/adapters/prisma`)
- **Supersedes**: D-034 (Auth.js / NextAuth v5)

### Context

Step 2.2.2 installed Auth.js v5 beta + `@auth/prisma-adapter`. The base integration compiled but could **not** work at runtime: the Auth.js adapter expects `User.emailVerified`/`image` and `Session.sessionToken`/`expires`, while ARIOT's schema uses `emailVerifiedAt`/`avatarUrl`/`tokenHash`/`expiresAt`. Renaming the frozen, already-migrated-and-seeded fields was a risky change. At this point ARIOT has **no live authentication users and no production authentication data**, so switching providers carries zero migration cost.

### Why Better Auth was selected

- **Free / open-source + self-hosted** — MIT licensed, no per-seat/MAU fees, runs on our own Postgres.
- **Next.js 16 App Router native** — official `toNextJsHandler` for `app/api/auth/[...all]/route.ts`; docs explicitly cover Next.js 16 (proxy replaces middleware).
- **Prisma 7 compatible** — works with the custom Prisma client output directory (`@/lib/generated/prisma/client`); adapter reads the client from that path.
- **PostgreSQL compatible** — `prismaAdapter(prisma, { provider: 'postgresql' })`.
- **Custom model + field names supported** — via `modelName` (e.g. `"User"`, `"Session"`) and `fields` mapping (e.g. `image → avatarUrl`, `token → tokenHash`, `ipAddress → ip`). Inspected the adapter source: it queries `prisma[modelName]` and resolves columns via `getFieldName`, so ARIOT's PascalCase models and business field names are preserved.
- **Database sessions** — default strategy; fits the existing `Session` model.
- **Preserves ARIOT RBAC** — Better Auth owns *authentication*; ARIOT's `Role`/`UserRole`/`permissions` JSON model remains the authorization source (`server/auth/permissions.ts`, later step). Not replaced by a comma-separated role field.
- **Future customer + B2B accounts** — same `User` identity core; Phase 3 `Customer` and Phase 5 `Account`/`AccountMember` extend the model without a new provider.
- **Low vendor lock-in** — self-hosted; user/session/role data stays in our Postgres.

### Why Auth.js was superseded (not retained merely because installed)

- The installed base could not function at runtime without renaming frozen fields or carrying a permanent adapter field mismatch (I-017).
- Current upstream guidance recommends Better Auth for new projects; Better Auth's Prisma adapter has first-class custom table/field mapping that fits ARIOT's conventions directly.
- Switching now (before any real auth data) avoids a costly later migration.

### Comparison vs installed Auth.js v5 (for this repo)

| Criterion | Auth.js v5 (installed) | Better Auth (selected) |
|---|---|---|
| Free / OSS | Yes (MIT) | Yes (MIT) |
| Self-hosted | Yes | Yes |
| Next.js 16 App Router | Yes | Yes (explicit docs) |
| Prisma 7 custom output | Yes | Yes |
| PostgreSQL | Yes | Yes |
| Custom field/table names | Rigid (expects exact names) | First-class (`modelName` + `fields`) |
| Compat with ARIOT schema | **No** (field mismatch) | **Yes** (mapped) |
| DB sessions | Yes | Yes (default) |

### Security implications

- Session token + `BETTER_AUTH_SECRET` (HMAC). `secret` read through typed `server/env.ts`; HTTP-only, Secure, SameSite cookies per `TECH_ARCHITECTURE.md` §11.
- OAuth-first admin sign-in preferred; credentials only where required (later step).
- RBAC enforced server-side only via `requireRole`/`requirePermission`; no client-only admin protection.
- Auth mutation endpoints must be rate-limited (extends `server/rate-limit.ts`).
- No real secrets/credentials in repo, `.env.example`, seeds, or docs.

### Cost / lock-in / migration

- **$0** library cost; runs on existing Postgres + Next.js host.
- Minimal lock-in: data lives in our Postgres. The adapter boundary is the only Better Auth-specific coupling; DB models stay if ever swapped.

### Schema changes made (Step 2.2.2)

- Added `emailVerified Boolean @default(false)` to `User` (Better Auth flag; `emailVerifiedAt` retained as ARIOT business field).
- Added `updatedAt` to `Session`.

- Replaced `VerificationToken` with `Verification` (`identifier`, `value`, `expiresAt`).
- Mapped fields: `user.image → avatarUrl`, `session.token → tokenHash`, `session.ipAddress → ip`.
- Kept PascalCase model names (`User`, `Session`, `Account`, `Verification`) and set `modelName` so the adapter resolves them.
